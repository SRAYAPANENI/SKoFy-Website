# Calling — how it must work, how it works today, and every gap

Audited 2026-10-12 against the code in `skofy-customer-app`, `skofy-service-provider-app` and `skofy-backend`. Both apps run the same call code (`services/callManager.ts`, `app/chat.tsx`, `components/call-overlay.tsx`), so every finding applies to both unless marked.

> **Phase 1 applied 2026-10-12** (not yet tested on devices): push once per call (`ws.py` `is_first_invite`), Android ring timeout 50 s, lock-screen call screen (`plugins/with-call-screen.js` — flags only while a call notification shows; Android 14 full-screen permission prompt), foreground service and CallKit call from the moment of dialing, ringback on the call audio route (`InCallManager.startRingback('_DTMF_')`), decline carries the call id, iOS keeps the CallKit call for the whole call (audio handed to WebRTC on `didActivateAudioSession`, hang-up/mute from the system UI). **Ringtone:** always the phone's own — Android's default ringtone channel + `'_DEFAULT_'` in-app; on iOS every incoming call now rings through CallKit (including one arriving while the chat is open), the only way to play the user's chosen ringtone. Re-verified the same day: a CallKit ring started by the open chat is stopped only when the caller hangs up (not on every screen cleanup); the in-app Accept answers through CallKit so it keeps holding the call; ending from the system UI while still connecting ends the call in the app too.

> **Phase 2 applied 2026-10-12** (not yet tested on devices):
> - **8 · Server call record** — `app/services/call_registry.py` (Redis) + `app/services/call_signaling.py`: one push per call, **busy** ("On another call"), server **no-answer timeout** (45 s), **"Ringing…"** for the caller (`call_ring` over the socket, `POST /calls/{job_id}/ringing` from a push), the reason a call ended (Declined / No answer / Busy) shown for a moment on the caller's screen, and **one call-log entry per call written by the server** (event `call`, with outcome and duration). An answered call whose apps died no longer keeps people "busy".
> - **9 · Incoming call from any screen** — on Android, a call arriving while the app is open elsewhere opens the full-screen incoming call (not while App Lock is showing); unanswered, it goes back to where the user was. *Not done:* moving the call engine out of `chat.tsx` into a separate service — it would rewrite the tested call code in both apps blind; the foreground service from dialing covers the main reason for it (A4). Logged in TECH_DEBT.
> - **10 · Call push queue** — `send_call_push` / `send_call_cancel_push` routed to a `calls` queue with its own worker (`celery_calls` in `deploy/docker-compose.prod.yml`).
> - **11 · Native call notification** — `plugins/with-call-screen.js` generates `CallStyleModule` (Android CallStyle: green Answer / red Decline, phone's ringtone looping, full-screen over the lock screen, 55 s timeout), `CallActionModule` (hands Answer/open to JS, queued on cold start) and `CallActionReceiver` + `CallDeclineTaskService` (Decline works even with the app killed — headless task `DodorezCallDecline`).
> - **12 · ICE restart** — on a dropped connection the caller restarts ICE (`call_renegotiate` / `call_renegotiate_answer`), both show "Reconnecting…", the call ends only if it isn't back within 20 s.
>
> Re-verified the same day: two people calling each other at once is not "busy" (the server follows the apps' rule — the higher user id's call wins, the other is withdrawn without a log entry); an offer for a call that's over is refused; the caller's "busy" can't arrive before the app knows it's calling; with App Lock on, an unanswered ring (full-screen or a tap) never opens the app — only Answer does — including on a cold start before the lock has loaded; App Lock no longer locks over a call being answered at startup.

> **Ringing redesign 2026-10-12** (after a device test: locked phone showed only "1 notification", vibration, no ringtone). A ringing call is now `CallRingerService` — a phone-call foreground service that plays the phone's own ringtone itself (`RingtoneManager` default ringtone, ring-mode aware: ring + vibrate / vibrate only / silent) and posts the CallStyle notification on a **silent** channel (`incoming_calls_silent_v1`), so a notification channel's frozen or OEM-muted sound can't silence a call. Its full-screen intent opens `IncomingCallActivity`, a native screen over the lock screen (turns the screen on; Accept → the app opens into the call over the lock screen; Decline → `CallActionReceiver`). If Android refuses the service, the old sound-channel notification is the fallback. Phones from makers that restrict this (Xiaomi, Oppo, Realme, OnePlus, Vivo, Huawei, Honor…) get a one-time prompt pointing to "Show on lock screen", "Pop-up windows", "Auto-start" and battery settings. All generated by `plugins/with-call-screen.js`.

> **Decision 2026-10-12 — contact only while the job is active.** Chat and calls are open from hire until the job is finished (`ACCEPTED`, `INSPECTING`, `INVOICE_PENDING`, `IN_PROGRESS`). Once a job is completed, cancelled, disputed or expired, no new messages and no new calls — the history stays readable and Book again is the way to work together again. Enforced by the server (`app/domain/job_contact.py`: `ChatService.send_message` → `JOB_CLOSED`; a new call on a closed job is refused with reason `job_closed`) and mirrored in both apps (call button greyed, message box replaced by a note). A call already in progress when the job closes isn't cut off.

**Legend:** ✅ works · ⚠️ partly · ❌ missing or broken. "Code" means confirmed by reading the code; "Device" means it also needs a test on a real phone to confirm the symptom.

## 1. The reference model — how a WhatsApp-style call works

A call is a **session**, not a screen. It lives in a background service that owns the connection, the audio and the timers; screens only display it.

| Stage | Caller sees | What the system does | Callee sees |
|---|---|---|---|
| Dial | "Calling…" + ringback tone in the earpiece | Server creates a call record (id, caller, callee, state=INVITED), sends **one** high-priority push to the callee, starts a server-side 45–60 s timeout. The caller's phone starts a foreground service immediately | — |
| Delivered | "**Ringing…**" (changes from "Calling…") | Callee's phone acknowledges the push → server tells the caller "ringing" | Full-screen incoming call over the lock screen, phone's own ringtone looping + vibration, green/red buttons (Android `CallStyle` + full-screen intent / `ConnectionService`; iOS CallKit) |
| Busy | "On another call" / call waiting | Server knows the callee is already in a call | A short beep, not a full ring |
| Answer | "Connecting…" → timer starts | Server marks ANSWERED and tells every other device of the callee to stop ringing | Call screen; audio routed to earpiece, proximity sensor on |
| Decline | "Declined" / "Busy" | Server marks DECLINED, cancels the push on all devices | Ring stops instantly |
| No answer | "No answer" | **Server** times out, marks MISSED | Ring stops; "Missed call" notification |
| Caller cancels | — | Server marks CANCELLED, sends a cancel push | Ring stops; "Missed call" |
| In call | Timer, mute, speaker, Bluetooth | Foreground service + system call integration (Android Telecom / iOS CallKit) keeps the process alive and lets the OS route audio and handle a cellular call coming in | Same |
| Network drop | "Reconnecting…" | ICE restart on the new network | "Reconnecting…" |
| Hang up | Call log entry | **Server** writes one call-log record (who, when, duration, outcome) | Same entry |

The rules that make it reliable:
1. One server-side record per call is the source of truth (state, timeout, log).
2. One push per call invite — never re-sent for the same call.
3. The ring always has its own timeout on the device, even if the cancel push is lost.
4. The incoming call UI is global and full-screen — it appears whichever screen the user is on, and over the lock screen.
5. The OS knows a call is in progress (Android Telecom/`ConnectionService`, iOS CallKit) for the whole call.

## 2. How Dodorez calling works today

- **The call lives inside the chat screen.** `app/chat.tsx` owns the `RTCPeerConnection`, the microphone, the timers and the state machine (`idle → calling/ringing/connecting → connected`). There is no call service outside the screen.
- **The server only relays.** `skofy-backend/app/api/v1/ws.py` forwards `call_offer / call_answer / ice_candidate / call_end / call_ready` between the two people on a job's socket. There is no call record, no server timeout, no busy state.
- **Waking the callee:** on every `call_offer` the server queues a Celery task (`send_call_push`) — Android gets a high-priority FCM data message (TTL 30 s), iOS a PushKit VoIP push.
- **Android ring:** the JS background handler (`registerBackgroundHandler`) shows a Notifee notification on channel `incoming_calls_v7` (phone's ringtone, created natively by `plugins/with-call-ringtone-channel.js`), `loopSound`, full-screen action that launches the main activity. `CallStyleModule` is referenced but **does not exist** in either repo, so the Notifee fallback is always what runs.
- **iOS ring:** `AppDelegate` (from `plugins/with-pushkit-voip.js`) reports every VoIP push to CallKit; JS listens with `react-native-callkeep`.
- **Answering from the notification** opens `/chat` with `autoAnswer`, which opens the socket and sends `call_ready`; the caller **re-sends its offer** and ICE candidates; the callee auto-answers.
- **Ending:** either side sends `call_end`; the server relays it and queues `send_call_cancel_push` so a phone that never opened the socket stops ringing and shows "Missed call".
- **During the call:** a Notifee foreground service (type `phoneCall`) shows an ongoing-call notification with Mute / Speaker / Hang up — started only once the call **connects**.
- **Call log:** each app posts its own SYSTEM chat message (`call_started`, `call_ended`).

## 4. Why the two reported symptoms happen

**"The ringtone has issues"** — in order of likelihood:
1. **Rings forever** when the caller's cancel doesn't arrive (D2) — no ring timeout on Android.
2. **Double ring / a second ring after opening the app** (C6) — the re-sent offer triggers another push.
3. **Ringback quiet or on the wrong speaker** on the caller's side (A3).
4. **Late or no ring when the app is killed** (B6, A8) — headless JS boot plus the shared push queue.
5. **Ringing during a call** (A6) — no busy state.

**"The calling screen has issues"**:
1. **No full-screen call over the lock screen** (B4, B5) — missing lock-screen flags and the Android 14 full-screen permission check.
2. **No incoming screen when the app is open on another page** (B2) — only a banner.
3. **Plain notification instead of a call-style one** (B3) — `CallStyleModule` doesn't exist.
4. **"Connecting…" then failure** after answering (A4, C2) — the caller's app was frozen in the background.
5. **iOS: answered on the lock screen, then nothing** (C7).

## 5. What's missing in the cycle — the fix list

Ordered by impact. Each item names where it lives.

**Phase 1 — stop the visible failures (apps + small backend change)**
1. **Push once per call** — backend sends `send_call_push` only for the first offer of a `call_id` (Redis `SET NX` with a 60 s expiry), not for re-sent offers. *Fixes C6, F2.* `ws.py`
2. **Ring timeout on Android** — `timeoutAfter` on the incoming-call notification (same as the caller's 45 s) and a missed-call notice when it fires. *Fixes D2, D3.* `callManager.ts`
3. **Lock-screen call screen** — config plugin adding `android:showWhenLocked="true"` and `android:turnScreenOn="true"` to `MainActivity`; on Android 14+ check `canUseFullScreenIntent()` and send the user to the setting once. *Fixes B4, B5.* `plugins/`
4. **Foreground service from the moment of dialing** — start the ongoing-call service when the caller taps Call, not on connect. *Fixes A4, A5.* `chat.tsx`, `callManager.ts`
5. **Ringback on the call route** — `InCallManager.start({ media: 'audio', ringback: '_DEFAULT_' })` instead of `expo-av`. *Fixes A3.*
6. **Decline carries the call id** — include `call_id` from the push in `sendDecline`. *Fixes C4.*
7. **iOS: keep the CallKit call for the whole call** — don't `endCall` on answer; end it on hang-up; report outgoing calls; activate WebRTC audio in `didActivateAudioSession`. *Fixes C7, E4.*

**Phase 2 — make it a real call system**
8. **Server-side call record** (Redis): `call_id → caller, callee, job, state, timestamps`. Server owns the timeout (missed), busy (callee already in a call → "busy" to caller), the "ringing" acknowledgement and **one call-log message** per call. *Fixes A2, A6, A7, D4, F1.*
9. **Global call service + incoming-call screen** in each app — the peer connection, audio and timers move out of `chat.tsx` into a call service; a full-screen `/call` route shows the incoming call from any screen. *Fixes B2, makes A4/D6 robust.*
10. **Dedicated push path for calls** — a separate high-priority Celery queue (or send directly from the API with the async client). *Fixes A8, F3.*
11. **Android call-style notification and system call integration** — build the native `CallStyle` notification (or self-managed `ConnectionService` through `react-native-callkeep`'s Android side) so the OS treats it as a call. *Fixes B3, E3, part of B6.*
12. **ICE restart on network change** with a "Reconnecting…" state. *Fixes D5.*

**Configuration (no code):** APNs VoIP key + `APNS_CUSTOMER_TOPIC` / `APNS_PROVIDER_TOPIC` on the server (B7, B8); confirm the TURN server is running (F4); on test phones, allow auto-start / disable battery optimisation (B6).

## 7. Duplicate call screen and stuck "Connecting…" (fixed 2026-10-12, apps — needs a new build)

**Symptom.** After tapping Accept, the screen sometimes sat on "Connecting…" forever. Pressing back revealed another "Connecting…" screen, even from inside the chat.

**Cause.** On a cold or background start, one Accept could reach the app by up to four routes: Notifee's background event, `getInitialNotification`, the native `CallActionModule` initial action, and the `pendingCall` AppState listener. `openCallScreen` only skipped a job whose chat was already focused. Each route pushed its own chat screen. One copy got the call; the others waited for an offer that never came.

**Fixes (both apps):**
- **One screen per call.** `openCallScreen` de-duplicates by `jobId:callId` for 60 seconds. A repeat answers the open screen instead of pushing another, and a pending call for the same job is cleared.
- **Retries while connecting.** The answering screen re-sends `call_ready` every 3 seconds (`CALL_READY_RETRY_MS`) until the offer arrives. The 15-second `CONNECTING_TIMEOUT_MS` still ends the attempt.
- **No double answer.** `answeringRef` blocks a second `handleAcceptCall` and ignores another copy of the offer while answering.
- **Back when the call ends.** A chat opened for a call (`autoAnswer` or `returnOnEnd` param) goes back when the call ends, whether or not it connected. This is skipped when nothing is behind it (a cold start).
- **No separate connecting screen.** "Connecting…" is no longer its own screen with a Cancel button. The in-call screen opens immediately with "Connecting…" as its status and Mute and Speaker dimmed until audio flows; End cancels. This matches WhatsApp.

**Re-verification of the fix (2026-10-12):**
- **Dedupe by job.** Some routes had no call id, so `jobId:` and `jobId:<id>` were treated as different calls. Dedupe is now by job, and two entries count as the same call if their ids match or either is missing. When a call ends, `forgetCallScreen` drops an entry that had no id, so the next call on that job still opens.
- **Accept while the call was still being fetched.** Accept arriving while the screen was still fetching the call used to be lost: the screen had no offer yet, so it rang again. Now `openCallScreen` records `acceptRequest`, and the chat answers as soon as the offer arrives (`takeAcceptRequest`).
- **Timeout during answering.** If the offer arrived near the 15-second mark, the connecting timeout could end the call mid-answer. Both connecting timeouts now skip while `answeringRef` is set. The `call_ready` retry stops once an offer is in hand.
- **Duplicate ringing.** A second offer could start the ring twice before React re-rendered. The ringing branch now sets `callStateRef` synchronously.
- **Screen before answering.** A screen opened from the notification body (not answered yet) showed the in-call screen. The overlay's `answered` prop now picks the screen: unanswered shows "Incoming call…" with Decline only, answered shows the in-call screen with "Connecting…".
- **Native side checked.** `CallActionModule.handleIntent` resets `intent.action` after handling, and `getInitialAction` is taken once, so an `onResume` doesn't re-fire Accept.
- **Note.** The call shows "connected" and the timer starts as soon as the answer is sent, not when audio actually flows. That's acceptable for now and is the same behaviour as before.

**Device test follow-ups (2026-10-12):**
- **The call now comes from the server.** "Connecting…" after Accept was the app waking up, opening its socket and then asking the caller's phone to resend the call (`call_ready`). The server now holds the unanswered call's offer (`offer_sdp` / `offer_type` on `call:{id}`) and the caller's candidates (`call_ice:{id}`, at most 40, 90-second TTL), and answers the callee's `call_ready` itself. If nothing is held, it falls back to relaying `call_ready` to the caller. Only the callee gets the held offer. It's dropped on answer or end. The remaining wait is the app starting and connecting, which can't be removed while the app isn't running.
- **Stuck on the splash screen after a call.** When the app was cold-started into a call, the splash route stayed underneath with its redirect skipped, so going back after the call landed on it for good. The splash (`app/index.tsx`, both apps) now redirects to home (or login) whenever it's focused again.
- **No ringtone when the app was open.** The in-app ring used InCallManager's `startRingtone`, which plays the ringtone file through its own MediaPlayer. That failed silently on phones with a custom ringtone, so only the vibration came through. Both rings now use `PhoneRinger` (plugin, `CallRinger.kt`), which uses Android's ringtone player and follows the ringer mode. The lock-screen ring reaches it through `CallRingerService`; the in-app ring goes through `CallStyleModule.startRingtone` / `stopRingtone` (`startInAppRingtone` in callManager). InCallManager remains as a fallback when the native module is missing. **This is native code: run prebuild.**
- **A call dropped after a short loss of network.**
  - The chat socket's reconnect backoff grows to 30 seconds, and the connection restart travels over that socket. A restart sent while the other phone's socket was down was also lost and never sent again, and the callee never asked for one. After the 20-second grace period, the call ended.
  - **Fixes:**
    - During a call the socket reconnects within at most 2 seconds, and immediately when NetInfo reports the network is back.
    - While reconnecting, the restart is re-sent every 3 seconds. A fresh restart is made at most every 8 seconds.
    - The callee asks the caller to restart with `call_restart` (a new signal type in ws.py).
    - The grace period is now 30 seconds.
- **Re-verification (2026-10-12).**
  - **Duplicate sockets.** A reconnect timer that had already fired still looked pending, so the network listener could start a second connect while one was in flight. That opened two sockets, and every message was handled twice. Now only the latest connect attempt may open a socket.
  - **Socket that stays dead silently.** After a network drop, the old socket can remain "open" without working for a long time. On any network change (offline → online, or Wi-Fi ↔ mobile data), the app now drops the old socket and opens a new one at once.
  - **Two rings at once.** Opening the app from the notification stops the native ring first (`cancelIncomingCallNotification`), so the in-app ring doesn't play on top of it.
  - **Deployed.** The server changes (held offer, `call_restart`) went live on 2026-10-12.
- **No call screen on a Samsung S25 (2026-10-13).** On Android 14 and later, a `phoneCall` foreground service needs `MANAGE_OWN_CALLS`, which neither app declared. `CallRingerService.startForeground` threw inside the service, after `show()`'s try/catch had already returned, so there was no screen, no ring and no fallback. The iQOO test phone didn't hit it. Fixes:
  - `MANAGE_OWN_CALLS` is added to both `app.json` files.
  - `show()` only starts the service when that permission is held.
  - The service catches a refused `startForeground` and posts the ringing full-screen notification instead.
  - **Native change: needs prebuild.**
- **Two calls from a double tap.** The Call buttons on the tracking screen (customer), and the home and navigate-to-site screens (provider), each pushed a chat with `autoCall`. Two taps on a slow network pushed two chats, and each placed a call. Fixes:
  - Those buttons ignore a repeat tap for 2 seconds (`callTapAllowed`).
  - Only one screen at a time can place a call (`claimOutgoingCall` / `releaseOutgoingCall`, released in `cleanupCall`).
- **Caller's photo on the call screens (2026-10-13).**
  - **Server:** the call push carries `caller_image`, the caller's `profile_image_url` for the role they're calling in (`ChatRepository.get_profile_image`), or `""` if there's none.
  - **Android native:** `CallerPhoto.load` fetches the photo once per call, scaled to about 256px with 4-second timeouts. The lock-screen `IncomingCallActivity` shows it in a circle, with the caller's initial until it loads. `CallRingerService` re-posts the CallStyle notification with the photo as the caller's icon. A slow photo never delays the ring.
  - **In-app:** the call screen gets the photo through `openCallScreen`'s `profileImage` param. Both chats now backfill the other party's photo from the job when it isn't passed: the customer chat uses `assigned_provider.profile_image_url`, the provider chat uses `customer_profile_image`.
  - **iOS:** CallKit has no custom images, so photos appear only in the app's own screen.
- **Re-verification (2026-10-13):**
  - **Call lock not released.** Leaving the chat while a call was still being set up (before `calling`) never released `claimOutgoingCall`, which blocked every later call until the app restarted. The chat's unmount now releases it.
  - **Stale incoming-call notification.** The photo update could re-post that notification just after the call was answered. The update now checks `currentJobId` under the same lock that `onDestroy` clears it with.
  - **Notifee fallback rejected.** Notifee refuses a notification with any non-string `data` value, so a call with no photo or id failed. Undefined values are now dropped.
  - **Known residual risk.** If Android refuses `startForeground` even though `MANAGE_OWN_CALLS` is held, stopping the service can still trigger Android's "did not start foreground" crash on some versions. This is expected to be very rare.
- **Device test (2026-10-14).**
  - **No voice in either direction while the app is in the background.** The ongoing-call foreground service (Notifee) was declared `phoneCall` only. Android silences the microphone of a backgrounded app unless its foreground service declares `microphone`. Fixes:
    - The service is now `phoneCall|microphone` (`with-call-foreground-service.js`).
    - `FOREGROUND_SERVICE_MICROPHONE` is declared in both `app.json` files.
    - `startOngoingCallNotification` passes both types.
    - **Native: needs prebuild.**
  - **A leftover "Incoming call…" screen with no name or photo after a call ended.** It showed "Customer" and the app logo and waited for a call that was over. Fixes, so that no route can do this:
    - The server answers `call_ready` for an ended or unknown call with `call_end` straight away. It never does this for a live answered call.
    - The app remembers calls that ended on the phone (`markCallEnded`, for 10 minutes), and `openCallScreen` skips them and anything without a `jobId`.
    - The Notifee catch-all handles only notifications that carry a `jobId`.
- **Samsung S25 still shows a banner, not the call screen, when locked (2026-10-15).** The likely cause is Android 14+'s "Full screen notifications" permission being off for Dodorez. Samsung often leaves it off for apps installed outside the Play Store. Without it, Android downgrades the full-screen call to a heads-up banner. The app asked only at launch, once a week, so one "Not now" left the phone banner-only for a week. Fixes:
  - The check also runs whenever the app comes back to the front, including on return from Settings. It asks at most once a day while the permission is off.
  - It never asks during a call (`pendingCall`, `ongoingCall`, answering, or a chat call in progress).
  - The prompt names the Samsung setting ("Allow full screen notifications").
  - **Not confirmed on the device yet.** If the permission is on and the S25 still shows a banner, capture `adb logcat` during a locked call. Look for full-screen-intent suppression or `CallRingerService` errors.
- **Calls ringing after logout (2026-10-15).** Logout only asked the server to delete this phone's push token. Any of these left the phone ringing: the request failed (no network, an expired login); the session expired instead of logging out; or the next person logged in on the same phone and the old token was still registered to the previous account. Fixes, in three layers:
  - **Server:** `upsert_fcm_token` first removes the same token from any other account. A phone rings only for whoever logged in there last.
  - **Logout (both apps)** goes through `signOutDevice()`. It sends the server logout, then calls `clearPushForSignOut()`, which stops any ringing (new native `CallStyleModule.cancelAll`), cancels all notifications, stops the call foreground service, and calls `messaging().deleteToken()` so Firebase forgets the token. Login registers a fresh token.
  - **Session expiry** runs `clearPushForSignOut()` too.
  - **On the phone:** the background and foreground push handlers ignore everything when there is no login, and delete the token. On iOS, a VoIP push for a logged-out phone is ended in CallKit straight away. A failed storage read counts as logged in, because iOS can refuse keychain reads while locked, so this can never silence a real call.
  - **Native change (`cancelAll`): needs prebuild.**
- **Status-bar call chip, like WhatsApp (2026-10-16).** With the app minimised during a call, there was no sign of the call in the status bar. You had to pull down the shade to find it. Android shows the green call chip with a live timer only for an ongoing-call `CallStyle` notification on a phone-call foreground service. Notifee can't build `CallStyle`. Fixes:
  - A new native `OngoingCallService` (`phoneCall|microphone`) and `OngoingCallModule`, in `OngoingCall.kt` generated by `with-call-screen.js`. The notification is `CallStyle.forOngoingCall` with a chronometer, plus Hang up / Mute / Speaker actions, on the same `ongoing_calls_v1` channel, so the lock-screen flags still apply. A tap on the notification or the chip brings the app to the front.
  - Actions go through `OngoingCallReceiver` to `CallActionModule.emit` (`ONGOING_HANGUP` / `ONGOING_MUTE` / `ONGOING_SPEAKER`) and are handled in `dispatchCallAction`. A Hang up with the app not running uses the `DodorezCallDecline` headless task.
  - **Fallback:** if `startForeground` is refused, the service emits `ONGOING_FAILED` and the app shows the old Notifee notification.
  - **Not yet tested on a device. Native change: needs prebuild.** The caller's photo isn't shown on this notification yet.
- **Echo (2026-10-14).**
  - **Expected:** two phones in the same room echo whatever the app does. One phone's speaker reaches the other's microphone through the air, and echo cancellation only removes the device's own playback. Test with the phones in separate rooms.
  - **Fixes for real echo:**
    - The call microphone now asks explicitly for WebRTC's voice processing (`CALL_AUDIO` in chat.tsx: `googEchoCancellation`, `googNoiseSuppression`, `googAutoGainControl`, `googHighpassFilter`). It used to rely on defaults.
    - Android uses WebRTC's own echo canceller and noise suppressor instead of the phone's hardware ones (`plugins/with-webrtc-audio.js` sets `WebRTCModuleOptions.audioDeviceModule` with hardware AEC/NS off). Hardware AEC is weak on many phones, and while it's on, WebRTC turns its own off.
    - **Native: needs prebuild.**

## Support calls (person ↔ agent), 2026-10-17

Voice calls on **support tickets**, separate from job calls. Code: `app/domain/support_calls.py` (rules), `app/services/support_call_service.py`, `app/api/v1/support_calls.py`, sockets `/ws/admin` and `/ws/support/{ticket}` in `app/api/v1/ws.py`; portal `src/components/calls/`; apps `services/call/supportCall.ts` + `app/support-chat.tsx`.

- **A call belongs to a ticket** and is between its customer/provider and the ticket's **assignee**. No assignee (new, or just escalated) → no call button; escalation therefore decides who you can call. An agent can only call a ticket at or below their support level, and only one that's theirs or nobody's (calling takes it).
- **Ringing**: the person's call rings the agent's portal (live line `/ws/admin`) — only if the agent has the portal open and isn't **Away** (sidebar switch, `admin_profiles.away`). The agent's call rings the person's phone **exactly like a job call** — the same `incoming_call` push (`send_call_push`) with `job_id = "support:<ticket>"` (`phone_call_key`): full-screen call and ringtone on a locked phone, Accept/Decline (Android CallStyle), CallKit via PushKit (iPhone). In `services/callManager.ts` that key opens the support chat instead of a job chat (Accept → it answers; Decline → `/support-calls/{id}/end`; missed-call tap → the support chat). Unanswered → `send_call_cancel_push` stops the ringing. Answered: ongoing-call notification (hang up / mute / speaker), CallKit told it connected/ended.
- **One live call per ticket** (partial unique index). Rings 45 s (in-process timer, like job calls); a call a restart left behind is settled the next time anyone looks.
- **Outcomes** are logged in the ticket conversation (`📞 Call with Priya · 4 min`, missed, declined). A **missed call from the person** sets `support_tickets.callback_requested_at` → "Call back" banner, list badge, sidebar count; answering any call on the ticket clears it.
- **Audio** through our media server, room `call-<call id>`, pass from `POST /support-calls/{id}/media` (participants only). **Recorded** under the same `CALL_RECORDING_ENABLED` switch (`call_recordings.ticket_id`; job_id now optional; same retention, held while the ticket is open).
- Escalating or closing a ticket cancels a call still ringing for it; an answered call carries on.
- Not built: a phone-network number (would need a telephony provider).
